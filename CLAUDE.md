# Dashhy — правила работы

## Два дерева, не одно

`project-dashboard/` — macOS. `windows/project-dashboard/` — Windows. Это две
копии одного приложения (93% строк совпадают дословно). Любая правка логики,
UI-строки, конфига или проверки безопасности вносится в **оба** дерева одним
коммитом — либо в теле коммита явно написано, почему только в одно.

Уже терялось:

- `_within` (`7ba9a11`, 09.07.2026) — починили только Windows, macOS прождал
  42 дня с обходимым регистром denylist.
- `.config/gh` / `.config/gcloud` — есть на macOS, при портировании на Windows
  выпали.

`tests/test_parity.py` прибивает то, что расходиться не должно: набор HTTP-роутов,
набор ключей `DEFAULT_CONFIG`, регистронезависимость denylist. CI гоняет их на
macOS и на Windows.

## Ребилд

- Правки `server.py` / `app.py` → обязателен `project-dashboard/build_app.sh`.
- Правки только `web/*` (html/css/js) → можно скопировать в
  `~/Applications/Dashhy.app/Contents/Resources/web/` без пересборки и без
  повторной выдачи Full Disk Access.

## Автозапуск — ловушка

`_login_launch_args()` подставляет `sys.executable` **того процесса, который
дёрнул тумблер**. Переключать автозапуск можно только из собранного
`Dashhy.app`, иначе LaunchAgent пропишется на dev-интерпретатор
(`/opt/homebrew/.../python3.14 server.py`) и будет молча поднимать не то.
Случалось 12.07.2026, чинилось руками. Windows: то же для `HKCU\...\Run`.

## Порты

Установленное приложение — 7777, dev — `DASH_PORT=7788`. Диапазон подбора
7777–7796, так что «занят» не значит «не запущен». Любая проверка «работает ли»
начинается с `lsof -nP -iTCP:7777-7796 -sTCP:LISTEN` и явного указания PID.
Сравнивать поведение двух портов, не убедившись, что это одна сборка, нельзя.

## Проверка сборки

`python3 project-dashboard/server.py --selftest` — поднимает сервер, дёргает
`/`, `/api/projects`, `/api/config`, печатает отчёт, выходит с кодом 0/1.
То же умеет собранный бинарь: `Dashhy.exe --selftest` (окно не открывается).
Отчёт можно направить в файл через `DASHHY_SELFTEST_OUT`. CI гоняет это и на
исходниках, и на собранном `.exe` — публикация релиза без прохождения self-test
не происходит.

## Релиз Windows

Два пути, оба через `.github/workflows/build-windows.yml`:

- **Катящийся.** Любой push в `main` пересобирает `.exe` и перезаписывает релиз
  под тегом `windows` — ссылка на скачивание остаётся прежней, тег переезжает на
  собранный коммит. Это то, что качает случайный человек.
- **Неизменяемый.** `git tag -a windows-v1.2.3 <sha> && git push origin windows-v1.2.3`
  публикует отдельный релиз под этим тегом, который больше никогда не
  переписывается. Так помечают версию, на которую можно сослаться.

Публикация физически невозможна без прохождения `Dashhy.exe --selftest` — шаг
стоит перед release. У PR сборка идёт, публикация отрезана условием на ref.
Каждый релиз несёт `SHA256SUMS.txt` и `build-manifest.txt` (pip freeze).

## Шестерёнка

`#settings-btn` — 4-я кнопка **внутри** `<nav class="mi-railnav">`, не прижата
к низу рейла (`margin-top: auto` убран осознанно). Уже откатывали один раз.

## Работа ведётся в репозитории

Многофайловые задачи пишутся в репо через `git switch -c <branch>` или
`git worktree add`, **не** в скретчпад. 06.07.2026 весь Windows-порт был написан
в `/private/tmp` и чуть не потерян — security-review прогнали по файлам, которых
в репо не существовало. Перед словом «готово» — `git status --short` должен
показывать ожидаемые файлы.

## Гигиена git

`git fetch` до первого коммита в сессии; в конце сессии `git status -sb` не
должен показывать `ahead`. Коммит `7ce2d80` пролежал непушнутым 38 дней и сел на
устаревшую базу — ветки разошлись, потребовался ребейз.

## Незакрытое

В браузерной консоли есть ошибка, видимая и в dev, и в собранном приложении.
Её текст ни разу не прочитан. Наблюдение «в консоли ошибка» без текста ошибки
наблюдением не считается.
